# Всему своё время — существующий сайт, обновление для PostgreSQL

Это доработка прежнего одностраничного приглашения, а не новый дизайн. Главная часть страницы, изображение, программа, цвета, шрифты и мобильные стили сохранены. Фамилия заменена на церковь. Добавлены необязательное окно участия и закрытый кабинет двух администраторов.

Сайт размещается на Vercel, исходники — на GitHub, постоянная база — Neon PostgreSQL либо другой PostgreSQL с TLS. Supabase больше не используется. Аккаунты администраторов создаются скриптом; публичной регистрации нет.

**Архив содержит код, но не ваши подключения.** DATABASE_URL, два секретных случайных значения и реальные email/пароли нужно настроить самостоятельно. Действующий сайт и его база этим архивом не изменены.

## 1. Подготовьте PostgreSQL

1. На [Vercel](https://vercel.com) откройте проект → Storage / Marketplace → [Neon](https://vercel.com/marketplace/neon/neon). Либо создайте проект на [neon.com](https://neon.com).
2. Выберите регион Франкфурт, если доступен. Сайт настроен на Vercel `fra1`.
3. Возьмите PostgreSQL connection string. Для Neon предпочтительна **pooled** строка (hostname содержит `-pooler`). Если интеграция создала переменную с другим названием, добавьте её значение также как **DATABASE_URL**.
4. Создайте базу/ветку для этого проекта. Схема находится в `database/001_postgres.sql`.

Если у прежнего сайта уже есть настоящие заявки в Supabase, сначала экспортируйте их и сохраните резервную копию. Они **не перенесутся автоматически** в Neon. Этот архив не имеет доступа к старой базе и не меняет её. Не запускайте новую схему в старой базе Supabase: названия таблиц совпадают, структура отличается.

## 2. Настройте проект локально

Нужны Node.js 22 и npm. Распакуйте архив и откройте терминал в папке, где лежит package.json:

```sh
npm ci
cp .env.example .env
```

Заполните `.env`:

| Переменная | Значение |
| --- | --- |
| DATABASE_URL | Полная строка подключения PostgreSQL из Neon |
| REGISTRATION_SECRET | Случайное значение длиной минимум 32 символа для квитанций заявок |
| IP_HASH_SECRET | Другое случайное значение длиной минимум 32 символа для хеширования IP |
| APP_ORIGIN | Для локальной работы `http://localhost:3000`; на Vercel можно оставить пустым |

Два разных секрета сгенерируйте двумя отдельными запусками команды:

```sh
node -e "console.log(require('node:crypto').randomBytes(32).toString('hex'))"
```

Не публикуйте `.env`. В `.env.example` оставлены только названия переменных с пустыми значениями. Никаких реальных секретов в архиве нет. Не используйте префиксы `NEXT_PUBLIC_` или `VITE_` для этих значений.

Внешнее подключение PostgreSQL использует TLS с проверкой сертификата и имени сервера (`verify-full`). Для локального PostgreSQL можно использовать localhost и отключённый SSL в собственной строке подключения.

## 3. Создайте таблицы

```sh
npm run migrate
```

Команда выполняет `database/001_postgres.sql`. Повторный запуск с этой же схемой безопасен: существующие заявки не удаляются. Альтернатива — выполнить весь SQL в Neon SQL Editor.

Таблицы:

- `invitation_registrations`: id, церковь, дети, участие, created_at; служебные поля для повторных запросов и удаления.
- `invitation_admins`: ровно два доступных слота, уникальные email, отображаемое имя и scrypt-хеш пароля.
- `invitation_sessions`: хеши серверных сессий и срок действия.
- `invitation_rate_events`: обезличенные ключи ограничений частоты запросов.

## 4. Создайте двух администраторов

Используйте **реальные разные email**. Адреса ниже — обозначение места, куда нужно поставить свой email, а не готовые аккаунты:

```sh
npm run admin:create -- --slot 1 --email ВАШ_EMAIL
npm run admin:create -- --slot 2 --email EMAIL_СЕРГЕЯ
```

Слот 1 — Тимофей, слот 2 — Сергей Власенко. Скрипт попросит пароль дважды, без отображения ввода. Минимум 12 символов, максимум 256. Пароль не передаётся в командной строке и не сохраняется в открытом виде. Скрипт требует интерактивный терминал.

Повторный запуск для того же слота меняет email/пароль и завершает старые сессии этого администратора. Третий слот запрещён ограничением базы. Скрипт запускается на вашем компьютере, не через публичный endpoint. Достаточно выполнить его один раз для каждого аккаунта. Если нужна смена пароля, запустите снова.

## 5. Проверьте сайт перед публикацией

```sh
npm run check
npm test
npm run dev
```

Откройте [http://localhost:3000](http://localhost:3000). Это настоящий сервер с PostgreSQL из `.env`, без имитации backend. Для тестирования перед мероприятием лучше использовать отдельную Neon-ветку, чтобы не добавлять тестовые заявки в рабочую базу.

Проверьте:

1. Отправьте церковь и 3 ребёнка: заявка сохраняется, затем открывается окно участия.
2. Сохраните текст «Наше участие» и убедитесь, что появилось подтверждение.
3. С другого браузера отправьте 5 детей, нажмите «Пропустить». Заявка остаётся, участие пустое.
4. Добавьте заявку на 2 ребёнка. В кабинете должны быть 3 заявки и 10 детей.
5. Войдите обоими администраторами; проверьте неправильный пароль.
6. Измените/удалите ошибочную заявку, убедитесь, что статистика пересчиталась.
7. Выйдите и убедитесь, что список закрыт. Проверьте на телефоне и iPad.

В проект включены автоматические проверки серверных сценариев и DOM-поведения формы. Они запускают настоящий PostgreSQL-движок **PGlite в тестах**. Это не рабочая база, не mock backend и не подмена Neon в приложении: рабочий сервер использует только `pg` + DATABASE_URL. Тестовые записи существуют только в памяти тестового процесса и не входят в опубликованный сайт.

При подготовке архива эти проверки прошли. Подключение к **вашему** Neon, действующие аккаунты и опубликованная версия не проверены: их настройки не предоставлены. Полноценная проверка внешнего соединения, Vercel cookie и визуального отображения на устройствах выполняется после подключения.

## 6. GitHub → существующий Vercel

1. В вашем GitHub-репозитории замените исходники содержимым архива. **Загружайте файлы и папки, а не ZIP.** package.json, package-lock.json, vercel.json, public/, api/, lib/ должны быть в корне репозитория.
2. При замене удалите старые файлы `api/config.js`, `lib/config.cjs`, `lib/register.cjs`, старые тесты, `database/setup.sql`, `database/add-admins.sql`, `PREVIEW.html` и `BUILD_PROMPT_RU.md`: они относятся к прежнему Supabase-подключению. Особенно важно удалить `api/config.js`, чтобы не оставлять старый публичный endpoint конфигурации.
3. Не загружайте `.env` и `node_modules`. Их исключает `.gitignore`.
4. В **существующем** проекте Vercel подключите этот репозиторий в Settings → Git. Если проект ещё не подключён, используйте Import Git Repository.
5. Framework Preset — **Other**. Root Directory — корень репозитория. Output Directory — **public**. Build Command — пустой (без override). Install Command — `npm ci`. Node.js — **22.x**.
6. В Environment Variables добавьте DATABASE_URL, REGISTRATION_SECRET, IP_HASH_SECRET для Production. APP_ORIGIN можно не создавать: сервер сверяет Origin с адресом запроса на Vercel. Если указываете APP_ORIGIN, используйте точный основной HTTPS-адрес без завершающего `/`; другие домены тогда не смогут отправлять формы.
7. Удалите ненужные старые переменные SUPABASE_* из проекта, когда убедитесь, что прежняя версия больше не нужна.
8. Выполните Deploy / Redeploy. После изменения переменных окружения тоже нужен новый deployment.

Для Preview используйте отдельную Neon-ветку и соответствующие переменные Preview. Оставляйте APP_ORIGIN пустым, чтобы уникальные адреса preview работали. Не переносите производственный localhost APP_ORIGIN на Vercel.

После подключения GitHub каждый push в production branch Vercel будет запускать новое развёртывание. Workflow `.github/workflows/checks.yml` выполняет `npm ci`, проверку синтаксиса и тесты. Vercel deployment обычно запускается параллельно: workflow сам по себе не блокирует неуспешный deployment. Для обязательной проверки до слияния включите required status checks в настройках защищённой ветки GitHub.

GitHub Pages для этого проекта не подходит: нужны серверные API и секреты. GitHub хранит код; Vercel запускает сайт и API; Neon хранит данные.

## Поведение формы

- Церковь обязательна: 1–100 символов после удаления крайних пробелов. Дети: целое число 1–1000.
- Кнопка блокируется до ответа. UUID запроса обеспечивает повторное сохранение без дубликата при двойном клике и сетевом повторе. После обновления страницы это новая форма и новый запрос.
- Основная регистрация сохраняется **перед** открытием окна участия.
- Текст участия необязателен, до 5000 символов. Сохранение и пропуск обращаются к API; при ошибке окно остаётся, введённый текст не теряется. Пропуск явно записывает NULL, даже если ответ на предыдущую запись потерялся.
- Escape до отправки участия закрывает окно, основная заявка остаётся. Закрытие вкладки также не отменяет регистрацию.
- Квитанция позволяет изменить только участие в конкретной своей заявке в течение 24 часов; список и чужие заявки недоступны. Не делитесь квитанцией.
- При ошибке базы основная форма не показывает ложного успешного сохранения.

## Безопасность и ограничения

- Все запросы PostgreSQL параметризованы. Названия и текст выводятся через `textContent`, без выполнения HTML.
- Административные чтение, изменение и удаление требуют серверной сессии и существующего администратора в базе.
- Cookie на Vercel: `__Host-lemgo_session`, HttpOnly, Secure, SameSite=Strict, Path=/, 12 часов. В базе лежит SHA-256-хеш случайного 256-битного токена. После выхода он отзывается.
- На локальном HTTP cookie называется `lemgo_session` и не содержит Secure; на Vercel Secure включается автоматически. JS никогда не получает значение cookie.
- Изменяющие запросы требуют совпадающего Origin и application/json; сторонний Origin отвергается, даже если cookie присутствует.
- Базовый антиспам: скрытое поле, блокировка повторов и лимит 10 новых заявок за 10 минут с одного IP. Общая сеть церкви делит лимит — при массовой регистрации лучше вводить одну групповую заявку. Для участия лимит 60 запросов за 10 минут; для входа 30 попыток на IP и 10 на email за 15 минут. Это базовая защита, не CAPTCHA.
- IP хранится только в виде HMAC; события старше суток очищаются при обращениях. Просроченные сессии удаляются при входах. Сырые пароли и тела запросов не логируются.
- Удаление заявки логическое: она исключается из списка и статистики, старый запрос не может её восстановить. Запись сохраняется как удалённая для защиты от повторов. После мероприятия организатор может окончательно удалить персональные данные SQL-командой из `database/cleanup.sql`.
- DATABASE_URL даёт серверу доступ к базе; браузеру не выдаются никакие ключи или соединения. Доступ к таблицам для PostgreSQL PUBLIC отозван. Не подключайте к этим таблицам публичный SQL/REST endpoint.

Официальные инструкции: [Vercel Functions](https://vercel.com/docs/functions/runtimes/node-js), [Neon на Vercel](https://vercel.com/marketplace/neon/neon), [TLS в node-postgres](https://node-postgres.com/features/ssl).
